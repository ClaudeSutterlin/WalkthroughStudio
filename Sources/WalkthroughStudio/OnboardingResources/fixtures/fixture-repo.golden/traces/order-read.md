# Read an order by id (GET get-order → OrderService.get → OrdersRepo.fetch)

**Scenario.** A read-order request that the (absent from this repository) hosting framework dispatches to handle_get_order(request, 42): a bare GET for order id 42 carrying no X-User header and no credential of any kind — say from an attacker walking ids 1, 2, 3, … — where the caller expects the row {"id": 42, "user_id": 7, "total": 29.99} back and gets exactly that.

## Hops

1. handle_get_order(request, 42) is entered by whatever framework binds the route (none exists in src/) and goes straight to the service: require_user is imported on L2 and called on L9 by the sibling create handler three lines above, but this handler never calls it and in fact never touches `request` at all, so the unauthenticated caller passes the only place an authorization check could live. [[code:src/api/orders_handler.py@fb63e78#L14-L16]]
2. OrderService() is constructed fresh for this one read and its __init__ hard-constructs OrdersRepo() with no injection seam, so a read request opens its own database resources before anyone has decided whether the caller may see the row. [[code:src/service/orders.py@fb63e78#L5-L7]]
3. OrdersRepo.__init__ calls psycopg2.connect("dbname=orders") with a hard-coded DSN — no host, user, password, sslmode or connect_timeout, so libpq environment defaults decide and the DATABASE_URL key in config/settings.example is never read — and this connection is never closed for or after the request. [[code:src/repo/orders_repo.py@fb63e78#L7-L9]]
4. OrderService.get(42) is a single delegating line that hands order_id to self.repo.fetch unchanged: the business-logic layer adds no ownership check, no redaction and no shaping on the read path, so the id the caller supplied reaches the SQL exactly as received. [[code:src/service/orders.py@fb63e78#L13-L14]]
5. OrdersRepo.fetch runs the parameterized SELECT id, user_id, total FROM orders WHERE id = %s with id alone and no user_id predicate, then unpacks fetchone() into a dict with no None guard (an unknown id raises TypeError here) — and because psycopg2 is not in autocommit and nothing commits, rolls back or closes, the SELECT leaves this session idle in transaction on the server. [[code:src/repo/orders_repo.py@fb63e78#L27-L31]]
6. The repo's dict is returned straight out of the handler with no serialization or response-shaping layer between them, so the caller receives another customer's user_id verbatim and a total that is a decimal.Decimal (psycopg2's mapping of NUMERIC(10,2)) rather than the Python float the create path returns — a value stdlib json.dumps refuses to encode. [[code:src/api/orders_handler.py@fb63e78#L16]]

## What scares me

- Anyone who can reach this endpoint can read every order in the system: handle_get_order never calls require_user, order ids are a SERIAL sequence, and fetch selects by id alone, so a loop over 1, 2, 3, … returns each customer's user_id and order total with no credential ever presented. Nothing on the path logs anything, so you would not find out from your own systems — you would find out from a customer, a researcher, or a dump appearing somewhere.
- Fixing this by pasting require_user into the handler would look right and still leak: the owner's user_id only exists after the row has been fetched, so the check would run on data that has already been read and would pass or fail on a header the same caller supplies. The real fix is a user_id predicate in the SELECT at orders_repo.py L27-L31, which is a different and larger change than the one a reviewer is likely to ask for.
- Every GET opens a psycopg2 connection that is never closed and, because nothing commits or rolls back the SELECT, leaves a session idle in transaction on the server. Ordinary read traffic therefore pins snapshots, blocks VACUUM and walks toward max_connections; the first visible symptom is unrelated — order creation starts failing inside OrdersRepo.__init__, before its retry loop, with no log line — so the outage will be diagnosed in the wrong place.
- Asking for an order that does not exist raises TypeError from orders_repo.py L31, because fetchone() returned None and row[0] was subscripted anyway. A deleted or mistyped id looks identical to a genuine bug in the repository layer, there is no 404 anywhere on this path, and whoever is on call sees a stack trace instead of a routine miss.
- The same order has two different types depending on how you got it: create returns the Python float the service computed, this path returns decimal.Decimal from NUMERIC(10,2). Standard json.dumps raises TypeError on a Decimal, so unless the hosting framework happens to install a custom encoder, this handler's response cannot be serialized at all — and if it can, a client comparing the create response to a later read sees 29.990000000000002 against Decimal('29.99') and calls it a reconciliation failure.
- If the database is unreachable but not refusing connections, the request blocks at psycopg2.connect for the operating system's TCP timeout: there is no connect_timeout, no statement_timeout, and the connect call sits outside the retry loop that protects the write path. Read traffic will pile up holding request threads long before anything raises.
- None of this is covered by a test. tests/test_orders.sh re-implements sum(price*qty) in a heredoc and never imports src/, so CI stays green if someone deletes require_user from the create handler too, breaks fetch, or changes the SELECT — and the handlers are perfectly testable with a plain object, since they only duck-type .json and .headers, so the absence of tests is a choice rather than an obstacle.
- One author has written every commit to src/ and six of the twelve commits in this repository touch orders_repo.py alone. The person who knows why fetch has no user_id predicate, and whether anything downstream depends on user_id being in the response, is a single point of failure for the fix as much as for the bug.
