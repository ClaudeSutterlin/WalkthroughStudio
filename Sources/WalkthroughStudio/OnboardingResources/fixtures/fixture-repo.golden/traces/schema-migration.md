# Apply a schema migration by hand (db/migrations/ → psql → schema.sql)

**Scenario.** An engineer decides the pending address split should finally ship to production: they open db/migrations/002_split_addresses.sql, read the header comment saying it is not yet applied, paste its seven lines into `psql` against the production orders database (the same database src/repo/orders_repo.py connects to as dbname=orders, holding one users row with email ada@example.com and address "12 Analytical Ave, London"), and then follow the unwritten convention by appending the same statements to db/schema.sql and flipping the header to "-- applied". They expect a new addresses table holding that postal address and a users table without the old column; what actually happens is that the addresses table is created empty and the address string is destroyed.

The path begins with a seven-line SQL file whose only state is a free-text first line ("-- NOT yet applied to schema.sql (see TODO there)"): there is no migration runner, no schema_migrations table, no environment name and no invocation anywhere in the repository, so "running" this path means a human pasting L2-L7 into psql. 3. The whole documented procedure is one sentence under ## Operations — "Migrations are applied by hand; see db/migrations/." — which names no order, no approver, no backup, no verification and no per-environment record, so everything else in this path is convention inferred from commit 8facb98 rather than instruction. [[code:README.md@fb63e78#L6-L9]]
4. Confirming that nothing automates the step: the deploy script scp's src/ to deploy@<env>.example.com and restarts the orders service, never opening a database connection, so schema changes travel through a completely separate manual channel from code with no ordering guarantee between them and once per environment rather than once per repository. [[code:deploy/deploy.sh@fb63e78#L1-L6]]
5. The first statement creates addresses (id SERIAL PRIMARY KEY, user_id INTEGER REFERENCES users(id), line1/city/country TEXT) and commits on its own; every column except id is nullable with no UNIQUE or primary-address marker, and no INSERT ... SELECT follows it, so the table arrives empty and will stay empty because no code in src/ writes to it. [[code:db/migrations/002_split_addresses.sql@fb63e78#L2-L6]]
6. The second statement, ALTER TABLE users DROP COLUMN address, autocommits separately and irreversibly deletes every stored postal address — plaintext PII that was never copied into the table created one statement earlier — with no pg_dump, snapshot or down script anywhere in the repository and no transaction tying the two statements together. [[code:db/migrations/002_split_addresses.sql@fb63e78#L7]]
7. Blast radius on running code: the repository's three literal SQL strings (INSERT INTO orders, SELECT ... FROM orders WHERE id, SELECT ... FROM orders WHERE user_id) name only orders columns, so no live query breaks when users.address disappears — the migration is safe today purely by accident of what the code happens not to read, and that safety is invisible to any check. [[code:src/repo/orders_repo.py@fb63e78#L20-L37]]
8. The stated blocker is false: OrderService only sums item prices and delegates to OrdersRepo, and `git log -S address -- src/` returns no commit across all 12 commits of history, so nothing in src/service has ever read users.address and the TODO holding migration 002 back cites a dependency that never existed here. [[code:src/service/orders.py@fb63e78#L1-L14]]
9. Step three of the convention is hand-editing the checked-in mirror: schema.sql already carries 001's ALTER verbatim under a "-- 001_orders.sql" comment (L13-L14), so the engineer must append 002's statements and delete the TODO on L16 — and until they do, the file that looks like the schema still declares users.address and knows nothing about addresses. 10. The path ends with no verification of any kind: CI's single job checks out the repo and runs tests/test_orders.sh, which asserts Python arithmetic in a heredoc and prints PASS without ever starting Postgres, so neither schema.sql nor either migration is loaded into a database anywhere in the pipeline and production is the first place the SQL is executed. ## What scares me

- Running migration 002 exactly as written deletes every customer's postal address: it creates the addresses table and drops users.address with no INSERT ... SELECT between them, and nothing in the repository takes a backup, so the data is gone the moment the second statement commits. You would find out from a support ticket, not from an error.
- The two statements are not wrapped in a transaction and there is no down script, so a failure or a Ctrl-C between them leaves the database half-migrated — addresses created, users.address still present, or the reverse — with no recorded state to tell the next person which half ran. The only way to find out is \\d users in psql.
- The '-- applied' marker is a single comment in git while deploy.sh targets any number of <env>.example.com hosts, each with its own database, so the repository literally cannot tell you whether staging, production or both have received 001 or 002. Anyone who trusts the header instead of inspecting each database is guessing.
- The stated reason 002 is blocked — the schema.sql TODO saying users.address 'is still read by src/service' — was never true: a pickaxe search over the whole 12-commit history finds no mention of address anywhere in src/. That leaves two bad outcomes: someone applies the migration believing the blocker is resolved without checking anything else, or nobody ever applies it because nobody trusts the note.
- The documented rollback (redeploy the previous commit) cannot undo this path at all; code and schema ship through unrelated manual channels, and after the DROP there is no artifact in the repository capable of restoring the column or its contents.
- No database is ever started in CI — the workflow runs a shell script that asserts Python arithmetic — so a typo, a wrong environment or a wrong order is discovered for the first time in production, against live data.
- The three-step convention (run the SQL, append it to schema.sql, flip the header) is written down nowhere; it can only be reverse-engineered from commit 8facb98. Skipping the second step is what makes schema.sql and db/migrations/ disagree, and nothing detects that drift.
- Both migrations were written by the only author in db/ who has never committed to src/, a bus factor of one on the only path that changes production data structure. If that person is unavailable, the person running psql is working from a nine-word README sentence.
