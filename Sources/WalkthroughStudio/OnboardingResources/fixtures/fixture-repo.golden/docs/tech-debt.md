# Technical debt register

## Ranked by severity

- **landmine** No code in this repository ever inserts into users, yet orders.user_id is a FOREIGN KEY to users(id), so on a freshly bootstrapped database every order creation fails with a ForeignKeyViolation until someone inserts user rows by hand with psql; there is no seed file. [[fact:F-lens-data-migrations-003]] [[code:db/schema.sql@fb63e78#L9]]
- **risk** Nothing in the repository backs up or restores the database (no pg_dump, snapshot, or restore step; deploy.sh never touches the database; README mentions neither), so applying migration 002's ALTER TABLE users DROP COLUMN address as written destroys every stored address with no in-repo recovery path. [[fact:F-lens-data-migrations-010]] [[code:db/migrations/002_split_addresses.sql@fb63e78#L7]]
- **risk** The pin's larger exposure is transitive: requests 2.19.0 requires urllib3>=1.21.1,<1.24 (resolving to urllib3 1.23 from June 2018, which OSV lists with 11 advisories, 5 of them HIGH), plus idna<2.8 and chardet<3.1, none of which appear in requirements.txt, so a scanner reading only the manifest undercounts the vulnerable surface. [[fact:F-lens-dependencies-004]] [[code:requirements.txt@fb63e78#L1-L2]]
- **risk** Redeploying the previous commit (the documented rollback) restores only code, not schema: no migration has a down script and 002 ends with DROP COLUMN users.address, so a code rollback after 002 is applied cannot bring the column or its data back. [[fact:F-lens-deploy-ops-006]] [[code:README.md@fb63e78#L8-L9]]
- **risk** Possibly: Because psycopg2 runs with autocommit off and the connection is never closed, every fetch() leaves its connection 'idle in transaction' forever and every failed execute leaves an aborted transaction open, so the per-request connection leak also accumulates open transactions that block VACUUM and exhaust Postgres max_connections (default 100) after roughly that many requests. [[fact:F-lens-deploy-ops-016]] [[code:src/repo/orders_repo.py@fb63e78#L27-L31]]
- **risk** psycopg2 connections default to autocommit off, and fetch and list_for_user execute a SELECT without commit or rollback on a connection that is never closed, so every GET leaves a session 'idle in transaction' on the server; combined with one new connection per request, this pins snapshots, blocks VACUUM and exhausts max_connections under read load, not just write load. [[fact:F-lens-security-tests-009]] [[code:src/repo/orders_repo.py@fb63e78#L8-L9]]
- **risk** Because the test never touches project code, a green CI run gives no signal about regressions in src/; the production incident class already seen (duplicate orders from the retry loop) would pass CI unchanged. [[fact:F-map-ci-012]] [[code:tests/test_orders.sh@fb63e78#L4-L7]]
- **risk** Migration 002 drops users.address in the same script that creates addresses, with no INSERT ... SELECT to copy existing address values across, so applying it as written destroys every stored address. [[fact:F-map-db-013]] [[code:db/migrations/002_split_addresses.sql@fb63e78#L2-L7]]
- **risk** Nothing in the schema prevents duplicate orders: there is no idempotency key or unique constraint on orders, so the repo's retry loop (which the production duplicate-order incident forced back from 3 to 2 attempts) can insert the same order twice with no database-level guard. [[fact:F-map-db-020]] [[code:db/schema.sql@fb63e78#L7-L11]]
- **risk** There is no rollback path in deploy/deploy.sh; the only recovery from a bad deploy is to redeploy the previous commit, and both the script comment and the README say so. [[fact:F-map-ops-005]] [[code:deploy/deploy.sh@fb63e78#L2]]
- **landmine** Nothing in the codebase reads settings.example, DATABASE_URL or any environment variable: the repository layer hardcodes psycopg2.connect("dbname=orders"), so editing the config file changes nothing at runtime. [[fact:F-map-ops-013]] [[code:config/settings.example@fb63e78#L1-L2]]
- **risk** Order creation has no idempotency key: the handler's own TODO admits that the repo's retry loop can double-insert an order when a transient error follows a successful commit. [[fact:F-map-src-005]] [[code:src/api/orders_handler.py@fb63e78#L7]]
- **risk** Every request constructs a new OrderService, which constructs a new OrdersRepo, which opens a new psycopg2 connection that is never closed, so each HTTP request leaks one database connection. [[fact:F-map-src-007]] [[code:src/api/orders_handler.py@fb63e78#L10]]
- **risk** Order inserts are retried without an idempotency key, so an OperationalError raised after conn.commit() succeeds (e.g. a timeout on the commit round-trip) re-runs the INSERT and creates a duplicate order. [[fact:F-map-src-028]] [[code:src/repo/orders_repo.py@fb63e78#L12-L18]]
- **landmine** The insert retry catches only psycopg2.OperationalError, so an IntegrityError (unknown user_id violating the FK) or DataError (total beyond NUMERIC(10,2)) propagates immediately and unhandled, while a failure to connect happens in OrdersRepo.__init__ outside the loop and is never retried at all; the retry covers only statement-time transport errors. [[fact:F-lens-data-migrations-004]] [[code:src/repo/orders_repo.py@fb63e78#L8-L9]]
- **landmine** OrdersRepo.insert returns the Python float total it was handed while fetch and list_for_user return decimal.Decimal (psycopg2's default mapping for NUMERIC), so the create response and a later GET for the same order differ in type and, after NUMERIC(10,2) rounding, can differ in value, and Decimal is not serializable by the standard json module. [[fact:F-lens-data-migrations-007]] [[code:src/repo/orders_repo.py@fb63e78#L20-L25]]
- **risk** orders.user_id is nullable (REFERENCES without NOT NULL) and handle_create_order forwards request.json['user_id'] untouched, so a body with user_id null and an X-User header of 'None' passes require_user (str(None) == 'None') and inserts an order attached to no user; the FK does not reject NULL. [[fact:F-lens-data-migrations-008]] [[code:db/schema.sql@fb63e78#L9]]
- **risk** No retention, archival or deletion exists for any table: the repository contains no DELETE, UPDATE, TRUNCATE, TTL or archive job of any kind, so users and orders grow without bound and every stored email and postal address is kept indefinitely. [[fact:F-lens-data-migrations-009]] [[code:src/repo/orders_repo.py@fb63e78#L22]]
- **risk** A user-erasure request cannot be served by one DELETE: orders.user_id references users(id) with no ON DELETE action, so deleting a user with orders fails with an FK violation, and because no code path deletes or nulls orders the only routes are hand-written SQL to delete the orders first or SET user_id = NULL (allowed, since the column is nullable).
