# Landmines

## Verify loop

The producer ran no build or test command, so nothing below was confirmed by execution.

## Numbered gotchas

1. CI never installs requirements.txt or any Python packages, so the smoke test cannot import psycopg2 or requests and a dependency breakage would go undetected. [[fact:F-map-ci-005]] [[code:.github/workflows/ci.yml@fb63e78#L6-L8]]
2. The workflow runs tests/test_orders.sh directly (not via bash), so it depends on the file's executable bit (100755) surviving in git; a checkout that drops the mode would make CI fail with permission denied. [[fact:F-map-ci-006]] [[code:.github/workflows/ci.yml@fb63e78#L8]]
3. The Python heredoc uses a quoted delimiter ('PY'), so bash performs no variable expansion inside it; anyone extending the test to pass shell variables into the Python block must unquote the delimiter or the values will be literal text. [[fact:F-map-ci-022]] [[code:tests/test_orders.sh@fb63e78#L4-L7]]
4. Because schema.sql already contains migration 001's ALTER, bootstrapping a database from schema.sql and then running the migrations folder fails on 001 with 'column created_at already exists'; only the header comment in each migration records whether it was applied. [[fact:F-map-db-010]] [[code:db/schema.sql@fb63e78#L13-L14]]
5. The schema.sql TODO says users.address 'is still read by src/service', but nothing in src/ (or templates/) references address at all, so the comment is stale or refers to code outside this repository; do not treat it as the reason 002 is blocked. [[fact:F-map-db-014]] [[code:db/schema.sql@fb63e78#L16]]
6. schema.sql contains no CREATE DATABASE and no connection setup; the repo hardcodes dbname=orders, so a newcomer must create a Postgres database literally named 'orders' and load schema.sql by hand before anything works (the DATABASE_URL key in config/settings.example is not what the code reads). [[fact:F-map-db-017]] [[code:db/schema.sql@fb63e78#L1]]
7. Because set -e stops the script between the scp and the ssh restart, a failed ssh leaves new code on disk under a still-running old process, and the next restart for any reason silently activates the untested code. [[fact:F-map-ops-007]] [[code:deploy/deploy.sh@fb63e78#L3-L6]]
8. Nothing in the codebase reads settings.example, DATABASE_URL or any environment variable: the repository layer hardcodes psycopg2.connect("dbname=orders"), so editing the config file changes nothing at runtime. [[fact:F-map-ops-013]] [[code:config/settings.example@fb63e78#L1-L2]]
9. No code renders or sends this template and no template engine is declared in requirements.txt, so the confirmation email is an unwired asset: adding it to the create-order flow is new work, not a config change. [[fact:F-map-ops-019]] [[code:templates/email.tmpl@fb63e78#L1-L3]]
10. The README gives no bootstrap steps: it never mentions config/settings.example, creating the 'orders' database, applying db/schema.sql, or installing requirements.txt, so a newcomer following it cannot run the service locally. [[fact:F-map-ops-026]] [[code:README.md@fb63e78#L1-L9]]
11. The pin is the source distribution psycopg2, not psycopg2-binary, so pip install compiles against libpq and fails on a fresh machine without Postgres development headers; pinning 2.8.6 also predates wheels for recent Python versions. [[fact:F-map-ops-032]] [[code:requirements.txt@fb63e78#L2]]
12. The create handler does no input validation: a body missing user_id or items raises KeyError before any business logic, and nothing in src/ maps that to a 4xx. [[fact:F-map-src-006]] [[code:src/api/orders_handler.py@fb63e78#L8-L11]]
13. require_user compares the header to str(user_id), so a JSON body user_id of 7 matches header '7' but a body user_id of '7' (string) also matches, and 7.0 does not ('7.0'); the type of user_id in the body silently changes authz outcomes. [[fact:F-map-src-014]] [[code:src/auth/authz.py@fb63e78#L9]]
14. Order line items are never persisted: the service passes items to OrdersRepo.insert, but insert forwards only user_id and total to _insert_once, so the database holds a total with no record of what was bought. [[fact:F-map-src-021]] [[code:src/service/orders.py@fb63e78#L11]]
15. db/schema.sql's TODO says 'users.address is still read by src/service', but nothing in src/ references users, address or any table other than orders, so that comment is stale and migration 002 is not actually blocked by src/service. [[fact:F-map-src-022]] [[code:db/schema.sql@fb63e78#L16]]
16. After a psycopg2.OperationalError the retry reuses the same self.conn without rollback or reconnect, so if the connection was dropped the second attempt fails too, and the final RuntimeError is raised without chaining the original OperationalError, hiding the real cause. [[fact:F-map-src-030]] [[code:src/repo/orders_repo.py@fb63e78#L13-L18]]
17. src/ has no web framework, no __init__.py packaging and no entry point that binds the handlers to routes, so a newcomer cannot run the service from this repository alone; the handlers only exist as functions that expect a request object with .json and .headers. [[fact:F-map-src-040]] [[code:src/api/orders_handler.py@fb63e78#L1-L3]]
18. No code in this repository ever inserts into users, yet orders.user_id is a FOREIGN KEY to users(id), so on a freshly bootstrapped database every order creation fails with a ForeignKeyViolation until someone inserts user rows by hand with psql; there is no seed file. [[fact:F-lens-data-migrations-003]] [[code:db/schema.sql@fb63e78#L9]]
19. The insert retry catches only psycopg2.OperationalError, so an IntegrityError (unknown user_id violating the FK) or DataError (total beyond NUMERIC(10,2)) propagates immediately and unhandled, while a failure to connect happens in OrdersRepo.__init__ outside the loop and is never retried at all; the retry covers only statement-time transport errors. [[fact:F-lens-data-migrations-004]] [[code:src/repo/orders_repo.py@fb63e78#L8-L9]]
20. OrdersRepo.insert returns the Python float total it was handed while fetch and list_for_user return decimal.Decimal (psycopg2's default mapping for NUMERIC), so the create response and a later GET for the same order differ in type and, after NUMERIC(10,2) rounding, can differ in value, and Decimal is not serializable by the standard json module. [[fact:F-lens-data-migrations-007]] [[code:src/repo/orders_repo.py@fb63e78#L20-L25]]
21. The '-- applied' header is one repository-wide flag while deploy.sh targets any number of environments (deploy@<env>.example.com), each with its own database, so nothing records which environment has actually received 001 or 002; the only way to know is to inspect each database's columns by hand. [[fact:F-lens-data-migrations-015]] [[code:db/migrations/001_orders.sql@fb63e78#L1]]
22. Applying a migration is an undocumented three-step manual convention that can only be inferred from commit 8facb98: run the SQL against each environment's database, append the same statements to schema.sql under a '-- <file>' comment, and flip the file header to '-- applied'; README says only 'applied by hand', and skipping the append step is exactly what leaves schema.sql and the migrations folder disagreeing. [[fact:F-lens-data-migrations-016]] [[code:db/schema.sql@fb63e78#L13-L14]]
23. Neither migration wraps its statements in BEGIN/COMMIT and neither has a down script, so running 002 with plain psql autocommits statement by statement: if DROP COLUMN fails after CREATE TABLE addresses succeeded the database is left half-migrated with no recorded state, and there is no reverse for either migration. [[fact:F-lens-data-migrations-017]] [[code:db/migrations/002_split_addresses.sql@fb63e78#L1-L7]]
24. The TODO's justification for not applying 002 ('users.address is still read by src/service') was never true at any of the 12 commits: a pickaxe search (git log -S address) over src/ and templates/ across the whole history returns nothing, so the blocker either concerned code outside this repository or was a misreading by the migration author, who never committed to src/. [[fact:F-lens-data-migrations-018]] [[code:db/schema.sql@fb63e78#L16]]
25. Whether psycopg2==2.8.6 even installs on a current interpreter is untested anywhere: its classifiers end at Python 3.8, it is the source distribution needing libpq headers, CI runs on ubuntu-latest's system python3 without ever pip-installing, and deploy.sh never ships requirements.txt, so the first person to run pip install -r requirements.txt on a modern machine is the first person to find out. [[fact:F-lens-dependencies-009]] [[code:requirements.txt@fb63e78#L2]]
26. scp -r overwrites and adds files on the host but never deletes, so a module removed or renamed in src/ stays importable on every host until someone cleans /srv/orders by hand. [[fact:F-lens-deploy-ops-002]] [[code:deploy/deploy.sh@fb63e78#L5]]
27. The host must be provisioned entirely out of band before the first deploy: the /srv/orders directory, the deploy user, an 'orders' systemd unit, a Python runtime with psycopg2 and a Postgres database named 'orders' are all assumed and none is defined anywhere in the repository. [[fact:F-lens-deploy-ops-003]] [[code:deploy/deploy.sh@fb63e78#L5-L6]]
28. The handlers import 'src.auth.authz' and 'src.service.orders', so the deployed process must run with /srv/orders (not /srv/orders/src) on sys.path; that working directory or PYTHONPATH is set by the systemd unit, which is not in the repository, so a unit that points at the wrong directory fails with ModuleNotFoundError on the first request. [[fact:F-lens-deploy-ops-004]] [[code:src/api/orders_handler.py@fb63e78#L2-L3]]
29. The environment argument is an unconstrained string used only as a hostname prefix, so 'prod', 'production' and a typo are all accepted without confirmation and resolve to different hosts; a production deploy has no guard beyond spelling the subdomain correctly. [[fact:F-lens-deploy-ops-007]] [[code:deploy/deploy.sh@fb63e78#L4-L5]]
30. The backoff sleeps after the final failed attempt too: on two OperationalErrors the loop sleeps 0.1s, retries, sleeps 0.2s, then exits and raises, so a doomed insert adds 0.3s of pure wait including a useless 0.2s after the last try. [[fact:F-lens-deploy-ops-015]] [[code:src/repo/orders_repo.py@fb63e78#L13-L18]]
31. vendor/generated/client_pb2.py is a protoc-generated stub for an 'orders' message that nothing imports, with no protobuf or grpc package in requirements.txt and no .proto source in the repo, so it hints at a planned gRPC integration that does not exist and cannot be regenerated from this checkout. [[fact:F-lens-deploy-ops-020]] [[code:vendor/generated/client_pb2.py@fb63e78#L1-L2]]
32. The retry loop only catches psycopg2.OperationalError and `range(2)` means two attempts total (one retry), so an IntegrityError (e.g. FK violation) or an InterfaceError from a connection that died mid-request escapes on the first occurrence, and the loop always sleeps 0.2s after the final failed attempt before raising RuntimeError. [[fact:F-lens-landmines-glossary-001]] [[code:src/repo/orders_repo.py@fb63e78#L11-L18]]
33. The literal `2` in `range(2)` is an incident-tuned constant, not a default: it shipped as 3 on 2025-01-22 and was reverted to 2 on 2025-01-28 after duplicate orders in production, so the obvious 'fix' for flaky inserts (raise the count) re-creates the incident, and the inline comment is the only guard against it. [[fact:F-lens-landmines-glossary-002]] [[code:src/repo/orders_repo.py@fb63e78#L13]]
34. There is no dependency-injection seam: OrdersRepo opens the Postgres connection in __init__ and OrderService constructs an OrdersRepo in its own __init__, so merely instantiating OrderService() (for example in a unit test) requires a reachable database named orders, which is why the only test avoids importing src at all. [[fact:F-lens-landmines-glossary-003]] [[code:src/service/orders.py@fb63e78#L5-L7]]
35. All intra-project imports are absolute from a top-level package named `src` (`from src.auth.authz import ...`), so the process must run with the repository root (the parent of src/) as cwd or on sys.path; running a module from inside src/ fails with ModuleNotFoundError: No module named 'src', and on the host deploy.sh lands the tree at /srv/orders/src/ so the systemd unit (not in this repo) must use /srv/orders as its working directory. [[fact:F-lens-landmines-glossary-004]] [[code:src/api/orders_handler.py@fb63e78#L2-L3]]
36. The type of `total` depends on the code path: create returns the Python float the service computed, while fetch returns psycopg2's default mapping of NUMERIC, which is decimal.Decimal, so the same order renders as 6.0 from create and 6.00 from get, and stdlib json.dumps on handle_get_order's result raises TypeError (Decimal is not JSON serializable) unless the hosting framework installs a custom encoder. [[fact:F-lens-landmines-glossary-005]] [[code:src/service/orders.py@fb63e78#L10-L11]]
37. The template's placeholders describe a render context that no code builds: `order` in this codebase is a plain dict {id, total} (or {id, user_id, total}) and `user` is never fetched anywhere (the repo only ever returns the integer user_id), and the dotted `{{ user.name }}` form is Jinja2 attribute-or-key syntax that str.format-style substitution would not accept, so wiring the email means choosing and adding a template engine plus writing a users lookup that does not exist. [[fact:F-lens-landmines-glossary-006]] [[code:templates/email.tmpl@fb63e78#L1-L3]]
38. vendor/generated/client_pb2.py says 'Generated by protoc. DO NOT EDIT' but the repository contains no .proto source, no protoc step in CI or any script, no protobuf runtime in requirements.txt, and nothing in src/ imports it, so it cannot be regenerated from this repository and a change to it can only be made by hand-editing a file that forbids hand edits. [[fact:F-lens-landmines-glossary-007]] [[code:vendor/generated/client_pb2.py@fb63e78#L1-L2]]
39. The '-- applied' / '-- NOT yet applied' marker is a comment in a file in git, so it is one flag per repository while deploy.sh targets any number of environments (<env>.example.com), each with its own database; the file cannot tell you whether staging or prod has migration 001 or 002, and there is no schema_migrations table to ask, so the only reliable check is inspecting the live database (e.g. \d orders in psql) before applying anything. [[fact:F-lens-landmines-glossary-008]] [[code:db/migrations/001_orders.sql@fb63e78#L1]]
40. deploy.sh ships the local working tree, not a git revision: `scp -r src` copies whatever is on disk, including uncommitted edits, untracked files and local __pycache__ directories (the repository has no .gitignore), and scp never deletes, so a module removed from the repo stays on the host and remains importable until someone cleans /srv/orders by hand. [[fact:F-lens-landmines-glossary-009]] [[code:deploy/deploy.sh@fb63e78#L2-L6]]
41. Nothing in the repository ever inserts a users row (no users handler, no INSERT INTO users, no seed script), yet orders.user_id REFERENCES users(id), so on a freshly bootstrapped database every create-order call fails with a ForeignKeyViolation, an IntegrityError that the retry loop does not catch, until someone inserts a user by hand in psql. [[fact:F-lens-landmines-glossary-010]] [[code:db/schema.sql@fb63e78#L7-L11]]
42. Authorization is an explicit per-handler function call, not middleware, so every new handler is unprotected by default; handle_get_order already demonstrates the failure mode by omitting require_user, and anyone exposing list_for_user through a new handler must remember to add the check themselves. [[fact:F-lens-landmines-glossary-011]] [[code:src/api/orders_handler.py@fb63e78#L6-L16]]
43. Because the DSN names only the database, host, port, user and password come from libpq's environment variables (PGHOST, PGPORT, PGUSER, PGPASSWORD) or ~/.pgpass, not from anything in this repository; the code therefore works on a developer machine with a local socket and peer auth and fails elsewhere with 'connection refused' or 'role does not exist', and the knob to fix it is PG* environment variables on the host, not DATABASE_URL. [[fact:F-lens-landmines-glossary-012]] [[code:src/repo/orders_repo.py@fb63e78#L9]]
44. The retry loop wraps only the INSERT; the connection itself is opened in OrdersRepo.__init__ at request time with no connect_timeout, so a database that is down or unreachable does not trigger a retry at all: the request either raises OperationalError immediately from __init__ or, for a black-holed host, blocks at psycopg2.connect for the OS TCP timeout before any handler logic runs. [[fact:F-lens-landmines-glossary-013]] [[code:src/repo/orders_repo.py@fb63e78#L8-L9]]
45. require_user looks up the literal key 'X-User' with a plain .get, so whether the check works at all depends on the (absent) hosting framework supplying a case-insensitive headers mapping; under a plain dict populated from lower-cased or WSGI-style header names every create request is Forbidden. [[fact:F-lens-security-tests-006]] [[code:src/auth/authz.py@fb63e78#L9]]
