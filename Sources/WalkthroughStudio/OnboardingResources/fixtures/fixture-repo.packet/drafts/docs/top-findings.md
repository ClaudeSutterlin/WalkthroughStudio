# Top findings

Written by the producer at hand-off. Claims cite code anchors in double brackets.

1. Reading an order is completely unauthenticated: handle_get_order never calls require_user, order ids are a SERIAL sequence, and OrdersRepo.fetch selects by id alone with no owner predicate, so anyone who can reach the endpoint can walk 1, 2, 3 and read every customer's user_id and order total [[code:src/api/orders_handler.py@fb63e78#L14-L16]] [[code:src/repo/orders_repo.py@fb63e78#L27-L31]] [[code:db/schema.sql@fb63e78#L7-L11]]. Pasting require_user into the handler would not close it, because the fix belongs in the SELECT.
2. The one authorization check in the codebase compares two values the same client sends, the X-User header and the body's user_id, so it enforces self-consistency rather than authorization and any caller who can set a header can act as any user [[code:src/auth/authz.py@fb63e78#L8-L10]] [[code:src/api/orders_handler.py@fb63e78#L6-L11]] [[commit:d7b0850aadb5334dca15c14081de583791b705fc]]. It is opt-in per handler, so every handler added from now on is unprotected by default.
3. Order inserts are retried without an idempotency key, so an OperationalError arriving after the commit already succeeded creates a second valid order with nothing to distinguish it; this already happened in production and the remedy was to lower the retry count from 3 to 2, which makes it rarer, not impossible [[code:src/repo/orders_repo.py@fb63e78#L11-L18]] [[code:src/api/orders_handler.py@fb63e78#L6-L11]] [[commit:27caac59e7c6dec5425b6e2bb60f0f23e7cac3bc]].
4. Every request constructs a new OrdersRepo, which opens a psycopg2 connection that is never closed, and because autocommit is off and the read paths never commit, each GET also leaves a session idle in transaction, so ordinary traffic walks toward max_connections, pins snapshots and blocks VACUUM [[code:src/repo/orders_repo.py@fb63e78#L7-L9]] [[code:src/service/orders.py@fb63e78#L5-L7]] [[code:src/repo/orders_repo.py@fb63e78#L27-L31]].
5. Nothing validates input and nothing maps a failure to a response: a body missing items raises KeyError, an unknown user_id raises IntegrityError from the foreign key, an oversized total raises DataError, and fetching a missing order subscripts None and raises TypeError, none of which the retry loop catches or the code turns into a 4xx [[code:src/api/orders_handler.py@fb63e78#L6-L11]] [[code:src/repo/orders_repo.py@fb63e78#L27-L31]] [[code:src/auth/authz.py@fb63e78#L4-L5]].
6. Migration 002 creates the addresses table and drops users.address in the same script with no INSERT ... SELECT between them, no transaction, no down script and no backup anywhere in the repository, so running it as written deletes every stored postal address [[code:db/migrations/002_split_addresses.sql@fb63e78#L1-L7]] [[code:README.md@fb63e78#L8-L9]].
7. Migration state is a comment in a file in git while deploy.sh targets any number of per-environment databases, so the repository cannot say which environment has 001 or 002; schema.sql already contains 001's ALTER, so bootstrapping from it and then running the migrations folder fails, and the TODO blocking 002 claims src/service still reads users.address, which a pickaxe search over the whole history shows was never true [[code:db/schema.sql@fb63e78#L13-L16]] [[code:db/migrations/001_orders.sql@fb63e78#L1-L2]] [[code:deploy/deploy.sh@fb63e78#L4-L6]].
8. Deployment copies the operator's local src/ working tree over scp and hard-restarts a single systemd unit, with no build, no version record, no health check and no rollback beyond redeploying a previous commit that nothing wrote down; CI never calls the script, so code can reach production having never passed CI or been pushed [[code:deploy/deploy.sh@fb63e78#L1-L6]] [[code:.github/workflows/ci.yml@fb63e78#L1-L8]] [[code:README.md@fb63e78#L6-L9]].
9. The entire test suite re-implements sum(price * qty) inside a bash heredoc and asserts it equals 6.0 without importing a single module from src/, so the handlers, require_user, the retry loop and every SQL statement have zero coverage, and neither of the two production-incident commits added a test [[code:tests/test_orders.sh@fb63e78#L1-L8]] [[code:.github/workflows/ci.yml@fb63e78#L6-L8]] [[commit:30bfa828b4b5a162bbb9c2bf9487ae82f3ace6c6]].
10. The items a customer ordered are summed into a float total and thrown away, because there is no order_items table and the INSERT persists only user_id and total, so after a dispute you can say what was charged but not what was bought, and the same order reads back as a Decimal that json.dumps cannot serialize [[code:src/service/orders.py@fb63e78#L9-L11]] [[code:src/repo/orders_repo.py@fb63e78#L20-L25]] [[code:db/schema.sql@fb63e78#L7-L11]].
